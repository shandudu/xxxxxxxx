# 销售订单交付执行与 OTIF 交付绩效 PRD V1.0

## 1. 目标

把 ATP/CTP 的交期承诺与实际发货、签收结果连接起来，形成：

> 销售订单承诺 → 备货/发货 → 客户签收 → OTIF 绩效 → 延期原因改善

OTIF（On Time In Full）按销售订单行统计：在承诺日期前完成客户签收，且签收数量达到订单数量，才算 OTIF。

## 2. 业务规则

### 2.1 交付状态

- \`OPEN\`：尚未足量发货，且尚未超过承诺日期。
- \`IN_TRANSIT\`：订单行已足量发货，但相关发货单尚未全部签收。
- \`OTIF\`：足量签收且签收时间不晚于 ATP/CTP 承诺日期。
- \`LATE\`：足量签收但超过承诺日期。
- \`NOT_IN_FULL\`：超过承诺日期仍未足量签收。
- \`LATE_AND_NOT_IN_FULL\`：已发生延期且同时未足量签收。

### 2.2 执行与签收

- 发货继续复用库存出库和批次质量放行校验。
- 发货单创建后记录实际发货数量，订单状态自动变为部分发货或已发货。
- 新增签收动作，写入 \`delivered_at\`；重复签收或取消状态不允许执行。
- 订单行的实际交付时间取覆盖该行全部数量的最后一张已签收发货单时间。
- 发货/签收后自动刷新订单行 OTIF 快照。

### 2.3 延期原因

延期原因优先读取当前 ATP/CTP 风险：\`SHORTAGE\` → 缺料，\`CAPACITY_RISK\` → 产能；无法匹配时记录为 \`EXECUTION\`，支持后续人工补充原因。

## 3. 统计口径

- 订单数、已完成订单数、在途订单数、延期订单数。
- 按订单行统计 OTIF、准时率、足量率、OTIF 率。
- 按延期原因统计数量和占比。
- 所有指标支持重新计算，历史快照保留承诺日期、实际签收日期、数量和状态。

## 4. 接口与页面

- \`POST /api/v1/erp/sales/shipments/{shipment_id}/deliver\`：登记签收；
- \`GET /api/v1/erp/sales/delivery/dashboard\`：OTIF 汇总；
- \`POST /api/v1/erp/sales/delivery/recalculate\`：重算全部非取消订单；
- \`GET /api/v1/erp/sales/orders/{order_id}/delivery-performance\`：查看订单行交付快照；
- 前端 \`/erp/sales/delivery\`：交付看板、延期原因和订单行明细。

## 5. 验收标准

- 发货和签收能正确更新订单状态、库存和交付快照。
- 足量且按期签收的订单行必须为 \`OTIF\`。
- 超期未足量签收必须进入延期状态，并能关联缺料/产能原因。
- OTIF 汇总与订单行快照一致，重算可重复执行。
- MySQL 迁移可升级/回滚，后端测试、前端类型检查和构建通过。
